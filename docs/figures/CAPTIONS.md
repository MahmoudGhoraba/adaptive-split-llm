# Figure captions (thesis figures 1–7)

All figures are generated by `docs/figures/make_figures.py` from existing results only (no new runs).
Testbed for every MEASURED value: MacBook Pro, Apple M2 (4 performance + 4 efficiency cores), 8 GB unified memory,
macOS 26.6.2, PyTorch 2.15.0; client on the CPU (fp16, 4 threads), server on the GPU via MPS (fp16), both on one
machine connected over TCP loopback with application-level network emulation; Llama-3.2-1B-Instruct.

**Figure 1 — Calibrated vs assumed latency model** (`fig1_latency_model.png`).
Predicted vs MEASURED end-to-end time of one request (prompt P = 256 tokens, answer A = 64 tokens, greedy) for the
splits (H, T) = (4, 2) (filled markers) and (2, 2) (open markers) under three emulated networks: Wi-Fi (50 Mbit/s,
RTT 20 ms), 4G (10 Mbit/s, 60 ms) and poor coverage (1 Mbit/s, 250 ms). Measured values are means of 3 repeats
(task 3, `runtime/check_out/task3_gens.csv`). Blue: calibrated model (MODELLED from FITTED per-side prefill/decode
parameters, output-layer and per-message costs, and the MEASURED idle-gap slowdown; `calibrated_model.latency_cal`),
−2.5 % to +0.6 % from the measurement. Orange: assumed model of the original controller (MODELLED with ASSUMED speeds,
client 10 GFLOP/s, server 1 TFLOP/s; `per_request_controller.latency`), +35 % to +387 %. Dashed: y = x. Both axes
logarithmic. The idle-gap factors were measured at (4,2), P = 128, so the (4,2) points are not fully independent of the
calibration; the (2,2) points are.

**Figure 2 — Per-phase breakdown of a decode step** (`fig2_decode_phases.png`).
MEASURED median time of one decode step (one generated token) for the split (H, T) = (4, 2), prompt P = 256, answer
A = 64, split into client compute (4 head layers, serialisation, 2 tail layers and the output layer on the CPU),
network and transport (round trip minus the server's handling time; includes the emulated RTT and serialisation at the
link rate) and server handling (10 middle layers on the GPU, including host–device copies). Loopback: 5 repeats without
network emulation; Wi-Fi, 4G and poor coverage: 3 repeats with application-level emulation (task 3, `task3_steps.jsonl`).
The network dominates from 4G downwards (67 of 113 ms; 317 of 379 ms on poor coverage); server time grows with the
network delay (17 → 28 ms) because of the idle-gap slowdown of Figure 3.

**Figure 3 — Slowdown after idle gaps** (`fig3_idle_gap.png`).
MEASURED median time per decode step of each component relative to its value without an idle gap, as a function of an
artificial idle gap inserted before every decode message (no network emulation; (H, T) = (4, 2), prompt P = 128,
answer A = 64, 3 repeats, 189 decode steps per gap). Shaded: 10th–90th percentile range. Absolute times at zero gap in
the legend. At a 250 ms gap the server's 10 layers (GPU) take 1.67 × and the client's 2 tail layers (CPU, the first
work after a reply arrives) 2.18 × longer; the cause (GPU/CPU power states) is not verified. These factors enter the
calibrated model (Figure 1) with the network time of a message as the gap.

**Figure 4 — Memory per side: measured vs modelled** (`fig4_memory.png`).
MEASURED peak physical footprint of each process (macOS `phys_footprint`, which includes GPU buffers) after a request
with prompt P = 1024 and answer A = 64, next to the MODELLED value of `memory_gb()` (fp16 weights + KV cache), for every
split (H, T). Left: client process on the CPU (embedding/output layer + H + T layers); measured = modelled + 0.40–0.41 GB
of fixed process overhead in 7 of 8 configurations (0.52 GB at (4,2), the only client that also loaded and removed
adapters). Right: server process on the GPU (U = 16 − H − T layers); the MPS allocator places every buffer ≥ 32 MiB in
1 GiB heaps, so the footprint grows in steps (2.57–2.58 GB for U ≥ 10, 1.45–1.49 GB for U ≤ 8) rather than with the
layer count; measured is 1.49–2.08 × the model. Dotted lines: 1 GiB and 2 GiB. Task 3, `task3_fit.json`.

**Figure 5 — Policies on the real runtime** (`fig5_policies_runtime.png`).
MEASURED total time of the same 30-request mobile trace (Wi-Fi → 4G → poor coverage → 4G → Wi-Fi, mixed privacy
classes, prompts 32–512 tokens, answer A = 64) for three controllers, 3 repeats each; the decisions were identical in
all repeats. Blue: request time including the per-request PING of the estimating policies; orange: time spent
reloading model weights when the configuration changes (on this single-machine testbed only one configuration fits in
8 GB, so client and server reload). Error bars: ± 1 standard deviation of the total over the 3 repeats. Diamonds:
predicted total (MODELLED: calibrated latency model + FITTED reload model). Switching-aware 208.4 ± 2.3 s, fixed per class
216.6 ± 10.9 s, adaptive 238.1 ± 16.3 s; the difference between switching-aware and fixed per class lies within the
run-to-run spread of fixed per class. `runtime/check_out/task4_real_trace.csv`.

**Figure 6 — Calibration impact: decisions that change between the assumed and the calibrated model**
(`fig6_calibration_impact.png`). Share of per-request decisions (split, protection) of the controller that differ
when the ASSUMED latency/memory model (`per_request_controller.latency`/`memory_gb`, assumed device of equal memory
budget given in brackets) is replaced by the calibrated model (`calibrated_model.decide_cal`), per device profile. Both
are MODELLED decisions; the calibrated profiles M2 with 4, 2 and 1 CPU threads are FITTED from MEASURED runs, their
memory budgets (4 / 2 / 2 GB) are ASSUMED; "assumed phone" and "assumed edge" are MODELLED sensitivity profiles.
(a) All four privacy classes: blue, a grid of 5 prompt lengths (32–1024 tokens) × 3 networks (Wi-Fi, 4G, poor
coverage) × 2 server loads (share 1.0, 0.25) per class; orange, the requests of the three 200-request traces
(stable 4G, mobile, server load) under their true conditions; labels give changed/total. (b) Traces, by privacy
class. On the M2 with 4 threads 327 of 600 trace decisions change (54.5 %), 84–89 % in the three private classes
(mainly split or secret options → all on client, because the assumed 20 GFLOP/s client is about 6.5 × slower in
prefill than measured); 2.3–3.8 % on the 2 GB profiles and the assumed edge; 0 on the assumed phone, whose calibrated
profile is scaled to the assumed speed. Answer length A = 128. SECRET_U from the current multisplit script only
(task 1); the result is identical to the run before task 1. `step5_per_request/task4_calibration_impact.csv`.

**Figure 7 — Leakage vs quality of the secret head + tail at all seven splits** (`fig7_multisplit_leakage.png`).
MEASURED on a Colab T4 (Llama-3.2-1B-Instruct, `secret_multisplit.py`, current script only): secret LoRA adapters
(rank 32) in the H client head layers and the T client tail layers, prompt-hiding weight λp = 0.1 and answer-hiding
weight λa = 0, 0.01, 0.03, 0.1 (the points of each line; agreement falls as λa rises). x: next-token agreement
with the public model (teacher-forced, WikiText; quality proxy). (a) Content leakage of the prompt to attacker A
(inverter trained on the public model) from the layer-H state. (b) Answer leakage: share of the client's next content
tokens matched when the server runs the PUBLIC tail and output layer on the state it returns (teacher-forced proxy).
Colour: H (light → dark: 1, 2, 4, 6, 8); dashed, open squares: T = 1; solid, filled circles: T = 2. Mean over training
seeds; error bars: half of max − min over seeds, only where more than one seed exists ((4,2): 3 seeds; (2,2): 2
seeds; all other splits 1 seed, no spread estimate). Dotted: limits of the controller's privacy classes (quality
75 %, prompt 80 %, answer 50 % / 40 %). Without adapters the prompt leakage is 97.6–99.98 % and the answer leakage
100 %. The prompt-leak seed spread reaches ±4.9–6.3 points against ≤ ±3.0 for answer leakage, so prompt-leakage
differences under about 10 points between splits are not reliable. `results/multisplit/measured_multisplit.txt`.
